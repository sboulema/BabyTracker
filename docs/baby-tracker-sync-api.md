# Baby Tracker sync API (reverse-engineered notes)

Findings from a static analysis of the Android app **Baby Tracker - Newborn Log**
(`com.nighp.babytracker_android`, version 6.04, APKPure build), decompiled with jadx 1.5.1.

**Status of this document**

- Everything marked *(code)* was read directly in the decompiled sources.
- Everything marked *(inferred)* is my reading of the code or of default library behaviour.
- **Nothing was tested against the live server.** No request was ever sent to it.
- This is a private, undocumented API of a third-party service. It can change without notice,
  and its terms of service may restrict third-party clients. Read them before building on this.

Relevant classes: `sync.SyncImple` (all HTTP calls and the sync loop), `sync.TransactionItem`,
`sync.TransactionLogOpCode`, `sync.DeviceSyncInfo`, `sync.UserInfo`, `data_objects.BCObject`,
`utility.GsonUtils`, `database.BTDatabaseImple` (log storage and merging).
Two methods did not decompile (`joinGroup`, `mergeTransactionLogsImple`), so the join flow and the
core merge logic are not fully read.

---

## 1. Concepts

| Term | Meaning |
|---|---|
| Account / group | An email + password account on the developer's server. All phones of one family log in to the same account. *(code)* |
| Device | One installation. Identified by a `DeviceUUID` (generated by the app) and a display name. *(code)* |
| Seed | A full copy of the database (`seed.zip`) plus the photos, uploaded by the first device so others can start from it. *(code)* |
| Transaction | One change (insert, update, delete, ...) to one object, serialized as JSON. *(code)* |
| `SyncID` | The local `TransactionLog.ID` of a transaction on the device that made it. Increasing integer per device. *(code)* |
| `MergedTransaction` | Local table: for every *other* device, the last `SyncID` of theirs that this device has merged. *(code)* |

**Every device has its own log.** A device pulls the log of each other device separately, using
that other device's UUID and the last `SyncID` it has already merged. There is no single global
sequence. *(code)*

---

## 2. Transport

- Base URL: `https://prodapp.babytrackers.com` *(code)*. A `https://dev.babytrackers.com`
  constant exists but is not used.
- Plain HTTPS with JSON bodies, except uploads, which are `multipart/form-data`.
- Authentication is a **session cookie**: log in once, then send the cookies on every request. *(code)*
- The app installs a trust-all TLS manager and a hostname verifier that always returns true
  (`trustAllHosts`, `DO_NOT_VERIFY`). *(code)* Any client of your own should verify certificates properly.
- `401` on any request means the session expired. The app logs in again and retries once. *(code)*
  `307` on a login attempt is treated as a failed login. *(code)*

### Login

`POST /session`, `Content-Type: application/json`

```json
{
  "EmailAddress": "user@example.com",
  "Password": "...",
  "Device": {
    "DeviceName": "Pixel 8",
    "DeviceOSInfo": "Pixel 8 OS 34",
    "DeviceUUID": "<app-generated uuid>"
  },
  "AppInfo": { "AccountType": 0, "AppType": 0 }
}
```

*(code: field names from `UserInfo`, `Device_Info`, `App_Info`, serialized with Gson.)*

- `200`: body is JSON `{"AccountID": <int>}`. The app stores the account ID when it first joins and
  compares it on every later login. If it differs, the app turns sync off and shows a login-failed
  warning. *(code)*
- `409`: not treated as an error message by the client. Meaning not determined. *(unknown)*
- Cookies from the response are stored and sent on later requests. *(code)*

`DELETE /session` disconnects this device (`200` expected). *(code)*

All statuses above are the ones the client checks for *(code)*. Response bodies were only read for
the login, device list and transaction list calls.

### Device list

`GET /account/device` returns a JSON array *(code)*:

```json
[ { "DeviceUUID": "…", "LastSyncID": 1234 } ]
```

`LastSyncID` is the newest `SyncID` the server holds for that device.

### Upload one transaction

`POST /account/transaction`, JSON body = one `TransactionItem`, expecting `201`. *(code)*

```json
{
  "OPCode": "TransactionLogOpCodeInsert",
  "SyncID": 57,
  "Transaction": "<Base64 of UTF-8 JSON, see section 4>"
}
```

`OPCode` is a Java enum serialized by Gson. Default Gson writes the enum **name**, as above
*(inferred, not verified on the wire)*. The values are:

| Name | Value in the local `TransactionLog.OpCode` column |
|---|---|
| `TransactionLogOpCodeInsert` | 0 |
| `TransactionLogOpCodeUpdate` | 1 |
| `TransactionLogOpCodeDelete` | 2 |
| `TransactionLogOpCodeRelive` | 3 |
| `TransactionLogOpCodeConflict` | 4 |

### Download transactions

`GET /account/transaction/{deviceUUID}/{lastSyncId}` returns `200` with a JSON array of
`TransactionItem`, oldest first *(inferred from the client loop)*. The client keeps requesting
while a response holds **500 or more** items, advancing `lastSyncId` to the last `SyncID`
received, so the server page size is probably 500. *(code / inferred)*

## 4. Transaction payload

`TransactionItem.Transaction` is `Base64( UTF-8( JSON ) )`. *(code)* The JSON is produced by Gson
with `setPrettyPrinting()` and a runtime type adapter that adds a discriminator property
**`BCObjectType`** holding the class name. *(code)* Registered types:

`Baby`, `Activity`, `BabyActivity`, `Bath`, `Bottle`, `ConflictRecord`, `EditableSelection`,
`Diaper`, `Feed`, `Formula`, `Growth`, `Journal`, `Joy`, `Medication`, `MedicationSelection`,
`Milestone`, `MilestoneSelection`, `Nursing`, `OtherActivity`, `OtherActivityDescription`,
`OtherFeed`, `OtherFeedSelection`, `Picture`, `Pump`, `Pumped`, `Sleep`, `Temperature`, `Vaccine`,
`VaccineSelection`, `NursingSession`.

Gson serializes every non-transient field of the class and its parents. For a `Diaper` that means
*(code, field list; exact JSON names not captured)*:

- from `BCObject`: `objectID` (the UUID), `newFlage`, `timestamp`
- from `Activity`: `note`, `pictureLoaded`, `pictureNote` (list of `Picture`), `time`, `timezone`
- from `BabyActivity`: `baby` (the **whole nested `Baby` object**)
- from `Diaper`: `amount`, `status`

`DiaperStatus` values: Wet = 0, Poopy = 1, Mixed = 2, Dry = 3. *(code)*

Object IDs come from `UUID.randomUUID().toString()`, i.e. **lowercase** hyphenated UUIDs. *(code)*

Not determined: the date format of `time` and `timestamp` (a custom `DateTypeAdapter` lives in a
dex file that was not decompiled), and the enum encoding of `amount` and `status`.

### Local storage

| Table | Columns | Use |
|---|---|---|
| `TransactionLog` | `ID` (autoincrement), `OpCode` (int), `Log` (the Base64 text above) | Upload queue |
| `MergedTransaction` | `DeviceID`, `SyncID` | Per remote device, the last merged `SyncID` |
| `PhotoList` | `PhotoFile` | Photos waiting to be uploaded |
| `PhotoDownloadList` | `PhotoFile`, `DownloadCount` | Photos waiting to be downloaded |
| `ReliveList` | `ID` | Objects whose deletion can be undone |

## 5. The sync loop

`checkNewTransactionRoutine` runs these steps in order *(code)*:

1. **Pull.** Log in if needed, `GET /account/device`, then for every device except this one:
   - if the device is unknown locally, download from `lastSyncId = 0`;
   - if its `LastSyncID` on the server is newer than the local `MergedTransaction.SyncID`, download
     from the local value;
   - repeat while a response holds 500 or more items.
   Each batch is handed to `mergeTransactionLogs(deviceUUID, items, ...)`.
2. **Download photos** listed in `PhotoDownloadList`.
3. **Push.** Take the oldest `TransactionLog` row (`ORDER BY ID LIMIT 1`), `POST` it, and when the
   server answers `201`, delete the row and continue with the next one. *(code for the queue,
   deletion after upload inferred from `deleteTransactionLogAndStartUploadNewTransaction`)*
4. **Upload photos** listed in `PhotoList`.

Consequences:

- The local `TransactionLog` is an **outbox**. On a phone that is online it is usually empty or
  short, so a clone will rarely contain the history of changes. The history lives on the server.
- A merge result is one of `Success`, `Ignored`, `Rejected`, `Error`. Merging dispatches on the
  opcode and the object type (`mergeInsert`, update, delete, relive, conflict). The detailed
  conflict rules were in the method that did not decompile.

## 6. What a third-party client (such as the website) would need

To appear as one more device and make phones pick up its entries, a client would have to:

1. Log in with the family's email and password, using its **own `DeviceUUID`** (the site would
   have to store those credentials).
2. Keep its own `SyncID` counter and upload one `TransactionItem` per entry, with a `Transaction`
   payload that the phones can deserialize and merge.
3. Also upload the photo file for picture entries (`POST /account/picture`).

Open questions that need a captured real exchange before any code is written:

- the exact JSON of each entry type, date format and enum encoding;
- whether the server accepts a transaction from a device it has never seen, and whether `SyncID`
  must start at 1 or be gap-free;
- what the `409` on login means;
- how the phones react to a transaction they cannot parse (rejected, ignored, or sync switched off).

Risks to weigh: the credentials the site would hold, an undocumented API that can change, the
extra device showing up in the family's device list, and a malformed transaction disturbing the
sync group. Try anything first on a separate throwaway account with two test devices.

A safe way to learn the real wire format is to capture the app's own traffic for a test account,
compare it with this document, and build an offline encoder that is tested against recorded
payloads before it ever talks to the server.

## 8. How the website implements this

Code: `src/Sync/`. The feature is off unless `BabyTrackerSync:Enabled` is `true`, and then per user on the profile page.

- `SyncTransactionBuilder` builds the transaction JSON of section 4 for diapers, formula, sleep, joy (also with a photo),
  activities, growth, temperature, milestones, medication, vaccines and supplements (`OtherFeed`).
  Dates are `yyyy-MM-dd HH:mm:ss +0000` in GMT, enums are written by name, insert transactions have `newFlage` true,
  and the selections and the baby are embedded as full objects read from the clone.
- `BabyTrackerSyncSession` logs in (`POST /session`), keeps the session cookies, uploads transactions
  (`POST /account/transaction`, 201) and photos (`POST /account/picture`, multipart field `picture`, the picture and
  its `__thumbnail` file).
- `SyncService` logs in per entry, checks that the account id is still the one it was set up with, uploads the
  transaction with the next `SyncID`, stores that counter, and then uploads the photo files. A failure never undoes the
  entry in the clone; it is reported on the page after adding.
- `SyncAccountStore` keeps the email address, password, device id and `SyncID` counter encrypted with the user's data
  key, in `Sync/{userId}.json.enc` next to the clone directories, so an import does not remove it.
- Guids are written to the clone as lowercase text, like the ids the Android app generates.

What is verified: the code builds, and `Check` style tests against a fake server confirm the requests, cookies, `SyncID`
counter, JSON shape and Base64 encoding described above.
What is **not** verified: anything against the real server or a real phone. In particular the enum encoding of `OPCode`,
whether the server accepts a transaction from an unseen device, whether the phones accept the payload as built, and the
`409` login answer. Capture the traffic of a test account first and compare it with the output of
`SyncTransactionBuilder` before pointing this at a real account.
